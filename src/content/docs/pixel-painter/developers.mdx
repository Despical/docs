## Implementation Documentation

The generated API reference is published at [javadoc.despical.dev/pixel-painter](https://javadoc.despical.dev/pixel-painter/). Its source is on [GitHub](https://github.com/Despical/PixelPainter). You can also generate class, method and package Javadocs locally using the [build instructions below](#build-locally).

These are implementation references. Pixel Painter does not currently publish a separate stable API artifact or register a dedicated Bukkit `ServicesManager` API. Do not assume that implementation classes are a versioned extension contract.

## Packages

| Package | Responsibility |
| --- | --- |
| `dev.despical.pixelpainter` | Plugin entry point and service lifetimes |
| `command` | ACF dispatch, argument validation, permission checks and Adventure panels |
| `config` | Bounded settings, literal message templates and configuration publication |
| `core` | World-independent positions, inclusive bounds, orientation and Oklab mathematics |
| `image` | Validated sources, palettes, resizing, diffusion and prepared plans |
| `service` | Bounded workers, region-aware scheduling, jobs, chunk ownership and restoration |
| `storage` | Copied journal records, binary persistence and startup recovery |
| `listener` | Quit and world-unload listeners that release painting resources |
| `listener` | Quit and world-unload listeners that release painting resources |

`PixelPainter` initializes configuration and services before registering commands. `ConfigurationManager` validates all resource candidates before changing active references. `TaskExecutor` owns two workers and a queue of eight waiting tasks. `PaintService` owns one world-operation slot, including waiting journal I/O.

## Thread Boundaries

`Scheduling` wraps Paper's global, region and entity schedulers. On Paper they all run on the server thread; on Folia each runs on the thread that owns the target. Block access happens only inside region tasks, one chunk batch at a time, and `PaintService` merges each batch result under its lock. Player messages and boss bars are sent through the player's scheduler. Image decoding, resizing, color matching, downloads and journal I/O run on bounded workers.

A prepared `PaintPlan` copies its pixel array and material counts. `Position`, `Bounds` and journal records identify geometry without retaining live worlds. Palette entries cache Oklab coordinates; their coordinate arrays must be treated as read-only when shared with workers.

Worker callbacks return to the global region thread while enabled. Queue rejection reaches the failure callback immediately. Shutdown may suppress a callback even when a journal write succeeded, so recovery must rely on durable records rather than callback delivery alone.

---

## Persistence Contract

A journal is saved and flushed before its painting can mutate terrain. Restart loading checks the binary format, ID/filename relationship, size bounds, coordinates and trailing content. Corrupt complete records fail loading and remain available for maintenance.

Restoration compares current data with the recorded original and target states. It preserves conflicts and retains the journal until restoration completes without conflicts. Changing the binary format requires migration planning and interrupted-operation tests.

## Build Locally

Use Java 25 and the checked-in Gradle wrapper:

```text
./gradlew clean build
./gradlew javadocJar
```

Windows uses `gradlew.bat` with the same tasks. The build produces:

| Output | Purpose |
| --- | --- |
| `build/libs/pixel-painter-2.0.0.jar` | Shaded server plugin, the only plugin artifact |
| `build/libs/pixel-painter-2.0.0-javadoc.jar` | Generated documentation archive, from `javadocJar` |
| `build/docs/javadoc/index.html` | Local HTML documentation entry point |

Javadoc validation treats warnings as errors. CI validates documentation separately from the ordinary plugin build. Follow the contribution and security instructions included with your source project before submitting changes.
